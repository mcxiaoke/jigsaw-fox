## 1. 问题陈述

熟练拼图玩家试玩后，**L1（1:1 为 25 片，最低难度）无法达成三星**。初步判断为数值偏严；深入分析后确认：这不是单点调参问题，而是**基准曲线的数学形式、阈值语义、以及「看原图/提示」等辅助成本口径同时存在缺陷**，且初版对「档位片数」的建模与系统真实结构不符（见 R1/R2）。

## 2. 现状实现

### 2.1 星级计算（`lib/logic/star_calculator.dart`）

```dart
static int calcStars({required int actualPieces, required double secPerPiece,
                      required int hints, required int seconds}) {
  final baseMs = (actualPieces * secPerPiece * 1000).round();
  final ms = safeSeconds * 1000;
  final timeScore = ms <= (baseMs * 7 ~/ 10) ? 3 : (ms <= baseMs ? 2 : 1);
  final allowance = hintAllowance(actualPieces);
  final hintScore = safeHints == 0 ? 3 : (safeHints <= allowance ? 2 : 1);
  final finalStars = timeScore < hintScore ? timeScore : hintScore;
  return finalStars < 1 ? 1 : finalStars;
}
```

### 2.2 档位与片数事实（v2 新增，甄别基线）

系统**不存在连续可调的片数**。`rows/cols` 只可能取 5 种宽高比 × 阶梯 multiplier（`puzzle_model.dart` L22-51）的乘积：

| 宽高比 | multipliers | 实际可选片数 |
|---|---|---|
| 1:1 | [5,6,8,10,12,15,20,24] | 25, 36, 64, 100, 144, 225, 400, 576 |
| 2:3 / 3:2 | [2,3,4,5,6,8,10] | 24, 54, 96, 150, 216, 384, 600 |
| 3:4 / 4:3 | [2,3,4,5,6,7] | 48, 108, 192, 300, 432, 588 |

- 30/31/40/41/75/76/125/126/200/201/320/321/450/451 等**均不可能出现**（难度选择器只展示 `_aspectRatio.tiers`，快照续玩 rows/cols 亦来自预设档）。
- `tierLevel` 分桶（≤30/≤40/≤75/≤125/≤200/≤320/≤450）仅是防御异常值的兜底；真实档位映射：
  - **L1**：24(2:3/3:2)、25(1:1) —— 3:4/4:3 无 L1（起步即 L2）
  - **L1.5**：36 —— **仅 1:1**
  - **L2**：48(3:4)、54(2:3)、64(1:1)
  - **L3**：96(2:3)、100(1:1)、108(3:4)
  - **L4**：144(1:1)、150(2:3)、192(3:4)
  - **L5**：216(2:3)、225(1:1)、300(3:4)
  - **L6**：384(2:3)、400(1:1)、432(3:4)
  - **L7**：576(1:1)、588(3:4)、600(2:3)
- **同档跨规格片数差最高达 56%**（L5：216~300）、L2 ±33%、L4 144~192(+33%)。旧设计（v3.3 §D4）正是为此用「实际片数 × 同档统一 s/片」保证跨规格公平（初版 v1 用代表片数曾导致 3:4 玩家被低估 8%）。

## 3. 根因分析

### 根因 A：三星线低于 UI 宣传下沿 —— 低档真实痛点，但需修正语义表述

选型界面告知玩家 L1「预计 1~3 分钟」，而三星要求 ≤52 秒：按最乐观的 1 分钟完成也只能拿 2 星。量化（按各档 1:1 代表）：

| 档位 | 三星线 | UI 预估下沿 | 三星线 / UI 下沿 |
|---|---|---|---|
| L1 | 52 秒 | 60 秒 | **0.88** |
| L1.5 | 88 秒 | 2.0 分 | **0.73** |
| L2 | 3.7 分 | 5.0 分 | **0.75** |
| L3 | 9.3 分 | 12.0 分 | **0.78** |
| L4 | 20.2 分 | 25.0 分 | **0.81** |
| L5 | 47.2 分 | 50.0 分 | **0.94** |

**修正表述（v2）**：
1. 旧设计 §4.1 写明的语义是「UI 区间 = 普通玩家用时（2 星线），3 星 = 快 30% 的挑战」，**三星线低于 UI 下沿是该语义的自然结果，不是未发现的 bug**。本方案主张翻转语义（见 §4.3），属于推翻 v3.3 设计决策，需产品确认，而非「修复缺陷」。
2. 但低档痛点真实存在：**L1/L1.5 这类短时局，固定成本（读图、理解交互、找第一块）占比极高**，52 秒对首次接触该 App 交互的玩家过于苛刻；L2 以上「快 30%」的高手语义尚可接受，L5 仅差 6%（50 分钟文案本就是约数）不应与 L1 并列论证。

### 根因 B：规模增长过陡 —— 方向性判断成立，但初版论证有缺陷（v2 修正）

拼图完成时间大体随片数超线性增长，但**初版用 L1(25,3.0) 与 L7(576,28) 两端点拟合出 b=1.712、并断言「实测合理区间 1.30~1.40」无数据来源**，且新公式 90×(576/25)^1.35≈1.73h 恰与自称的「L7 实测 1.7h」重合，存在循环论证，均不可作为缺陷证据。

按旧表分档拟合并列（对 1:1）：

| 区间 | 斜率 b（lnT vs lnN） |
|---|---|
| 25→64 | 1.54 |
| 64→144 | **2.08** |
| 144→400 | 1.72 |
| 400→576 | 1.31 |

**真实失衡是两端的绝对水平，而非单一指数**：低档 3.0s/片×0.7 后 2.1s/片过低（短时局固定成本被摊到「每片」导致三星不可达）；高档 25~28s/片使 Base 高达 2.8~4.5 小时，星级失去区分度。**正确做法是重建曲线后埋点校准（§8），而非引用未经证实的外来经验值。**

### 根因 C：提示是硬门槛（属实）

`hints == 0 ? 3 : ...` 且 `finalStars = min(timeScore, hintScore)` ——只要用过 1 次提示，星级封顶 2 星。额度（2 次）只决定「降到 2 星还是 1 星」，不决定能否三星。与 2.5 的代码一致。

### 根因 D1：计时口径不合理（属实）

`game_page.dart` L94-101：`initState` 中 `_startTimer()` 与 `_loadImage()` 并行，计时从进入页面即刻开始，包含图片解码/切块生成耗时；`didChangeAppLifecycleState`（L104-114）切后台仅 `flushSync` + 上报游玩时长，**不暂停计时**；无空闲检测。对 L1 这种 90 秒量级关卡，开局加载数秒即 3%+ 误差，中途离开 2 分钟则三星无望。

### 根因 D2：免费「看原图」停表 = 最大的激励漏洞（v2 新增，初版遗漏）

`game_page.dart` L994-1000：看原图按钮同时置 `_isPaused = _showOriginalImage` → **看原图期间完全停表、不限次数、零成本**。对比之下：
- 提示：花钱购买 + 冻结 1.5s（`_hintPauseUntil`）+ 用 1 次即封顶 2 星；
- 看原图：免费、无限次、全图参考（最强辅助）却不计任何代价。

**最强辅助反而最廉价**，而初版 §6.3 还把「看原图暂停」列为「保留」，等于把最大漏洞原样保留。若目标真的是「激励无辅助速通」，必须先处理看原图（§5.4），否则提示软扣减的改造意义减半。

### 根因 E：同档跨规格片数差被「1:1 中心假设」掩盖（v2 改写）

初版整段「档位边界断崖」（30→31、40→41、75→76…）**基于系统不可能出现的连续片数，系伪命题，已删除**（§2.2）。真实且被忽略的问题是：
1. **同档片数跨规格差最高 56%**（L5：216~300），初版数值表/UI 文案却只按 1:1 单值描述；
2. 旧模型用「同档统一 s/片 × 实际片数」维持跨规格相对公平（v3.3 D4）；若新模型改为按实际片数套连续幂律，同档 48 vs 64 片的三星线差将从「线性公平」变成约 10% 的幂律差（§4.5），**这是对 v3.3 公平机制的推翻，需产品决策**，初版默认其成立未加讨论。

### 根因 F：纯幂律缺固定成本项 → 低档必严（v2 新增）

星级失衡集中低档、高档失真的典型成因：**拼图存在不随片数归零的固定启动成本**（读图、理解交互、热身、找第一块）。`T = c·N^b` 无常数项时，低档时间被压到人手/认知极限以下（L1 三星=52s），高档却因幂律放大而虚高——**无论怎么调锚点与指数都修不好这把「剪刀差」**。需在模型中加入常数项或低档下限（§4.2）。

## 4. 新方案：基准曲线重建

### 4.1 设计原则

1. **自洽性**：UI 预估下沿必须 ≤ 三星线（玩家达到宣传最快即可三星），且星级窗口与预估区间同源；
2. **语义翻转**：Base 从「竞速基准」改为「熟练玩家典型用时」；
3. **函数式基准**：评星直接由 `actualPieces` 经连续函数得 Base，**不再经档位查表**——彻底消除档位边界突变，s/片仅作 UI/展示换算（v2 修正初版 R9 的矛盾表述）；
4. **跨规格公平是可证而非默认**：任何改变「同档同 s/片」取舍的方案都须显式评审（§4.5）。

### 4.2 基准模型

```
Base(N) = a₀ + c·N^b           （c = Base(25) / 25^b）
```

- **a₀（固定启动成本项）**：缓解根因 F。当前无真实数据，占位 `a₀ = 0`，但实施时对 ≤36 片局建议套用低档保护 `Base(N) = max(Base(N), 75s)`，待 §8 埋点后拟合真实 a₀。
- **占位参数（待校准，非实测值）**：`Base(25)=90s`（熟练典型，初版亦如此；产品可在 90~120s 间取值）、`b=1.35`。即占位公式 `Base(N) = 90 × (N/25)^1.35`（1:1 语义），锚点与指数**仅作首版占位**，上线后必须按 §8 用真实分布替换。
- `secPerPiece(N) = Base(N)/N` 仅用于展示层换算，不再是评星输入。

### 4.3 阈值语义（产品确认：推翻 v3.3「2 星=Base」语义）

| 星级 | 条件 | 含义 |
|---|---|---|
| ★★★ | `有效用时 ≤ 1.00 × Base` | 熟练玩家典型表现 |
| ★★ | `有效用时 ≤ 1.90 × Base` | 普通玩家从容完成 |
| ★ | 完成即得 | 保底 |

对比现状（3 星 0.70×Base、2 星 1.00×Base）：三星窗口整体放宽、语义从「快 30% 高手」改为「熟练典型」；二星窗口从 1.0 扩到 1.9。**需产品明确认可该语义翻转（推翻 v3.3 §4.1 显式决策）。**

> 读取方式：某 3:4 图选 L2（48 片）→ 三星线 3.6 分；某 1:1 图选 L2（64 片）→ 5.3 分。星级按实际片数实时计算，天然正确；**UI 文案与「档位级」成就/解锁若仍按档位单值，会与区间脱节**（决策见 §4.5）。

### 4.5 边界与跨规格连续性（v2 改写）

- **档位边界**：片数离散（§2.2）且评星改为连续函数后，「跨桶跳变」在数学上不再存在（同档不同片数的 Base 由函数连续给出）。初版 §4.5 的「最大跳变 62%→25%」表随伪命题一并删除。
- **跨规格同档**（需产品决策，选项 2 选 1）：
  - **选项 X1（推荐）**：评星直接按函数式 Base(actualPieces)。同档不同规格因片数不同而阈值不同（如 48 vs 64 片：3.6 vs 5.3 分）——绝对难度随片数走，公平性语义为「按片数幂律」；档位仅作 UI 分组。
  - **选项 X2**：维持 v3.3「同档统一 s/片」的相对公平（视觉上同档内大图/小图星级易达成度一致），函数只用于生成每档的档内代表 s/片。代价：同档内保留约 ±10% 的模型偏差。
  - 两种选项对玩家可见差异有限，但**影响文档 §4.4 表 B 的语义**，需先定再实施。

## 5. 提示机制改造（v3 语义已确认采纳）

### 5.1 现状问题

硬门槛：`hints == 0 ? 3 : ...`，用 1 次提示即失去三星资格；额度只区分 2/1 星。

### 5.2 新方案：等效加时（软扣减）

```
额度内  → 不扣星
超额    → 每次增加 (15% × Base) 的等效用时
有效用时 = 实际用时 + max(0, hints − allowance) × 0.15 × Base
```

超额 1 次 → +15% Base（多半从 3 星滑到 2 星）；超额 2 次 → +30%；超额 4 次 → +60%。平滑降级、可解释、易测试，保留「少用提示更快」的正向激励。

### 5.3 额度同步放宽

`allowance = (pieces / 40.0).ceil().clamp(3, 12)`

| 档位 | 片数(1:1) | 旧额度 | 新额度 |
|---|---|---|---|
| L1 | 25 | 2 | 3 |
| L1.5 | 36 | 2 | 3 |
| L2 | 64 | 2 | 3 |
| L3 | 100 | 2 | 3 |
| L4 | 144 | 3 | 4 |
| L5 | 225 | 5 | 6 |
| L6 | 400 | 6 | 10 |
| L7 | 576 | 6 | 12 |

### 5.4 看原图与提示统一语义（v2 新增决策项）

看原图（L994-1000）现为免费停表。为让辅助成本口径一致，建议（产品 3 选 1）：
- **Y1（推荐）**：看原图不停表（仅停摆盘交互），等效于「用时间换参考」——辅助代价显性化，零代码复杂度（删掉 `_isPaused = _showOriginalImage`）；
- **Y2**：停表但计入「参考次数」，超档位额度后并入提示等效加时（语义与 §5.2 统一）；
- **Y3**：维持现状免费停表（不推荐：与根因 C/D2 的改造目标直接冲突）。

## 6. 计时与空闲改造

### 6.1 三项修正

| 项 | 现状 | 修正 |
|---|---|---|
| **起表时机** | `initState` 与 `_loadImage()` 并行，进入即计时 | 拼图块生成完毕、首次可交互后才起表；加载期间计时器显示 `00:00` |
| **切后台** | 仅 `flushSync` 存档，不暂停计时 | 同步暂停计时，回前台恢复 |
| **空闲挂机** | 全程计时 | 连续无有效操作 ≥90 秒 → 计时暂停，任意有效操作恢复 |

**有效操作定义**：拼图块拖拽（开始/移动/放置）、画布平移缩放、提示请求、撤销、看原图开关。

### 6.2 活跃计时模型（v2 重写：删除初版「暂停 + 结算补回预算」双机制）

初版 §6.2 设计「idle 期间 UI 停表、结算时把超 0.5×Base 的 idle 补回」，但 §10.3 又称 `_idleSeconds` 不必持久化——**中途退出/续玩会清空累计、使豁免预算多次重置，可被续玩绕过**；且「UI 停表 + 结算补时」玩家感知割裂。v2 简化为：

```dart
bool _isIdle = false;          // 连续 90s 无有效操作置 true（UI 显示暂停标识）
int _idleSeconds = 0;          // 仅统计用，不参与评星

int get _activeSeconds => _seconds;  // _seconds 只在非暂停/非 idle 时累加 → 天然活跃时间
```

- 结算/存档/成就一律使用 `_seconds`（活跃时间）；挂机天然不计入，**无需预算、无需补回、无绕过漏洞**。
- `_seconds` 现有三处复用需在改动中同步核对口径：快照 `elapsedSeconds`（恢复时直接回填，语义不变）、`_reportPlaySeconds()` 成就累计（挂机不再计入「游玩时长」，行为更合理，需在成就侧文案确认）、结算 `timeSeconds`。
- idle 阈值 90 秒沿用初版；切后台与 idle 均只置暂停，不重复计数。
- `_idleSeconds` 是否持久化到快照仅影响统计展示，不涉及公平性，可后置。

### 6.3 暂停源统一（v2 更新）

统一为 `_isTimingPaused` 聚合判断：

| 暂停源 | 位置 | 处置 |
|---|---|---|
| `_isPaused`（结算弹窗） | game_page.dart L711 | 保留 |
| `_hintPauseUntil`（提示动画冻结 1.5s） | game_page.dart L633 | 保留 |
| `_isPaused`（看原图预览） | game_page.dart L994-1000 | **按 §5.4 决策处置（默认不再免费停表）** |
| 空闲挂机 | 新增 | 按 6.2 实现，置 `_isIdle` |
| 切后台 | `didChangeAppLifecycleState` L104-114 | 新增暂停（复用 `_isPaused`） |

## 7. 待定项：高阶档位收紧幅度

**需产品决策。** 低阶（L1~L3）放宽已无争议；高阶（L4~L7）是否同步收紧（按 §4.2 公式），三方案如下。

### 方案 A：全量收紧（推荐）

采用 §4.4 表 A 完整数值。曲线贴合 b=1.35 幂律（占位），三星恢复含金量。
- 优点：模型自洽，长期只调「锚点 + 指数」两个参数
- 风险：高阶玩家主观感受变难；且参数未经验证（§8 校准前勿全量铺开）

### 方案 B：温和收紧（幅度减半）

L1~L3 同方案 A；L4~L7 收紧幅度减半：

| 档位 | 片数 | s/片（B） | 三星线 | 相对现状 |
|---|---|---|---|---|
| L1 | 25 | 3.60 | 1.5 分 | +71% |
| L1.5 | 36 | 4.09 | 2.5 分 | +67% |
| L2 | 64 | 5.00 | 5.3 分 | +43% |
| L3 | 100 | 5.85 | 9.8 分 | +4% |
| L4 | 144 | 7.52 | 18.0 分 | −11% |
| L5 | 225 | 10.21 | 38.3 分 | −19% |
| L6 | 400 | 13.48 | 1.5 小时 | −23% |
| L7 | 576 | 15.19 | 2.4 小时 | −23% |

- 优点：折中；缺点：曲线偏离幂律、跨档落差回升，且参数表更接近「拍脑袋」，校准后仍需重设。

### 方案 C：只放宽低阶，高阶不动 —— 不推荐

否决理由同初版：会造成 L3→L4 档间大幅落差（相对公式值 L4 偏高），跨档挫败感强。

### 决策建议

倾向 **方案 A + §8 校准前置**：A 的自洽性使后续只需校准两个参数；但**校准未完成前不建议直接上线 A 的全量数值**，可先用 A 数值 + 埋点灰度。方案 B 的折中表在未来校准后无保留价值。

## 8. 埋点校准计划

**重要前提**：§4.2 锚点（Base(25)=90s）与指数（b=1.35）为**占位假设，非本项目真实数据**，首版上线后必须按真实分布校准。

### 8.1 上报字段

在 `game_page.dart` `_handleSolved()` 中上报（沿用 v2 活跃时间口径）：

| 字段 | 说明 |
|---|---|
| `canonicalId` | 拼图唯一标识 |
| `difficultyKey` / `actualPieces` / `tierLevel` / `aspectRatio` | 难度维度（含宽高比，v2 新增：分规格统计） |

| `hintsUsed` / `referenceViewedCount`(若实施 Y2) | 提示次数 / 看原图次数 |
| `stars` | 最终星级 |

### 8.2 校准规则（v2 修正：P50 → 分位对齐语义）

按 `tierLevel × aspectRatio` 分组聚合（样本 ≥200 局/组），用分布分位拟合模型参数：

```
3 星线基准：取 P25 ~ P30（接近熟练玩家，与「Base=熟练典型」语义一致）
2 星线基准：取 P70 ~ P85（普通玩家从容完成）
若 |P30 − Base| / Base > 20% → 以 P30 重设该组 Base
a₀（固定成本）：以低档（L1~L2）残差拟合，勿用 P50 整体平移
```

校准周期：上线后 2 周首次校准，此后每月一次；旧数据加权衰减。

### 8.3 验收指标

| 指标 | 目标 |
|---|---|
| L1 熟练玩家三星率 | 60%~80% |
| 各档位三星率分布 | 无档位 < 15% 或 > 60% |

## 10. 风险与兼容性

### 10.1 已得星级不受影响

`progress_store.dart` L360 `math.max(oldRecord.bestStars, stars)`：历史最佳星级取 max，高阶收紧不会剥夺已获三星，仅影响未来重玩刷新。

### 10.2 经济系统影响

高阶三星率下降 → 金币产出与「三星解锁」放缓；采用方案 A 时建议同步评估金币奖励表。

### 10.3 存档兼容

`elapsedSeconds` / `hintsUsed` 字段语义不变（活跃时间口径一致），旧存档可正常续玩。新增 `_idleSeconds` 仅统计，非评星输入，不持久化不影响公平性（v2 修正初版矛盾）。

### 10.4 跨规格公平决策风险（v2 新增）

§4.5 X1 会改变 v3.3 刻意维持的「同档同 s/片」相对公平（L2 内 48 vs 64 片星级达成难度出现约 10% 幂律差）。上线前需在「按片数算基准（X1）」与「同档统一 s/片（X2）」间定论，并补对应单测。

### 10.5 回滚

改动集中在 3 个源文件 + 1 个测试文件；保留旧 s/片表常量与 `StarCalculator` 旧签名（加可选参数）便于快速切换。
