### F2：模糊档位池的数值承诺不成立（实测数据）

终稿 §2.3 声称档位池「屏幕模糊半径**近似恒定 ~7px**」。按终稿给出的 `[7.0, 3.5, 2.5]` + 阈值 `(1.0, 2.0]` 实测：

| `s` | 命中档位局部 r | 屏幕半径 | 相对 7px 偏差 |
| :--- | :--- | :--- | :--- |
| 0.21（2×2 托盘） | 7.0 | 1.47px | −79% |
| 1.0 | 7.0 | 7.00px | 0% ✓ |
| 1.001（刚跨阈值） | 3.5 | **3.50px** | **−50%** |
| 2.0 | 3.5 | 7.00px | 0% ✓ |
| 2.001（刚跨阈值） | 2.5 | **5.00px** | **−29%** |
| 2.4（20×20 maxZoom） | 2.5 | 6.00px | −14% |
| 3.6（30×30 maxZoom） | 2.5 | 9.00px | +29% |

**问题本质**：档位池的局部半径按 `7/s_midpoint` 设计（中间值 ≈7px），但在**每个档位的端点上必然偏离**。终稿 §4 只承认「±2px 级跳变」，实际单点偏差可达 3.5px（−50%）。

**但这一项是否真的是缺陷，取决于一个终稿未给出的设计意图**：

- 若目标是「**屏幕恒定**」→ 档位池方案本身与目标冲突，应改用 2.4 节的动态除法思路（但 `MaskFilter` 不可变，需接受每帧 1 次分配，或改用 `Paint.maskFilter` 之外的替代）
- 若目标是「**避免放大后光晕过大**」→ 当前实现**已经达到目的**（s=2.4 时 6.0px vs 不处理的 16.8px），43% 偏差可接受，只需**修正文档措辞**为「屏幕半径控制在 3.5~7px 区间」而非「恒定 ~7px」

**建议**：采纳后者（改措辞），成本最低。因为 `_dragShadowPaint` 全局同时最多 1 个集群在拖拽，视觉阶跃不可感知——终稿 §4 的结论方向对，只是「≤2px」这个数字要改成「≤3.5px」，且「仅 1 块碎片」应改为「仅 1 个拖拽集群」。

### F3：两处 `scale` 口径不一致（需写进注释）

终稿 §2.2 定义 `s = scale.x > 1.0 ? scale.x : 1.0`，而紧随其后的视锥剔除（未改动）使用原始 `scale.x` / `scale.y`。同一函数内两个变量名高度相似、含义不同：

```dart
// 视锥剔除（保留原逻辑）：使用原始 scale
final left = position.x - (oh.left * size.x + margin) * scale.x;

// 新增逆缩放：使用截顶后的 s
final s = scale.x > 1.0 ? scale.x : 1.0;
```

**评估**：逻辑上**无错**（剔除本就该用真实缩放，线宽才需要截顶），但极易被后续维护者误统一。建议在 `s` 的声明处补一行注释说明「剔除使用原始 `scale`，二者不可合并」。

## 3. 对其他三份评审的裁决

三份评审共 24 条问题中，**2 条被裁定为误报**，其余结论有效且已被终稿采纳。

### 3.1 误报：bd 的 P0-1「`clamp` 返回 `num` 导致编译失败」

bd 断言：

```dart
final shadowOffsetY = (0.8 / curScale).clamp(0.3, 0.8);
canvas.translate(0, shadowOffsetY);  // ✗ 编译错误：num 不能赋给 double
```

**经 `flutter analyze` 实测验证为误报。** 原因：`0.8` 是 `double` 字面量，故 `0.8 / curScale` 的**静态类型是 `double`**；Dart 的 `double` 类型上覆写了 `clamp`，返回类型为 `double`，而非基类 `num.clamp` 的 `num`。

复现验证（临时脚本，已清理）：

```dart
void translate(double dx, double dy) {}
void main() {
  final s = 2.0;
  final b = (0.8 / s).clamp(0.3, 0.8);
  translate(0, b);   // flutter analyze → 仅 info 级提示，无 error
}
```

**影响**：终稿 §1.1 的 A4 条目把该误报列为「三方一致、必须采纳」，并据此选择了「改用 `max`/三目 + 除法，天然返回 `double`，无需 `.toDouble()`」。**结论（不用 `.toDouble()`）恰好是对的，但理由是错的**——终稿无需为一条不存在的错误调整设计。建议将 A4 从「必须采纳」降级或删除，避免后续维护者据此学到错误认知。

其余 bd 结论（P0-2 漏项、P1-1 表格矛盾、P1-2 `_maxZoom` 脱节、P1-3 行动项遗漏、P1-4 1x 未披露）**全部成立且已被终稿正确处理**。其中 P1-4 提出的「相对基线缩放」正是终稿采纳的路线，是本轮交叉评审最有价值的产出。

### 3.2 误报：gm 的 2.4「暗线与高光等宽会 100% 互相覆盖」

gm 断言：

> 拼图碎片相邻拼合时，左碎片的右边缘（暗线）与右碎片的左边缘（高光线）的贝塞尔路径**几何完全重合**……如果两边线宽完全相同（同为 1.0px），后绘制的碎片边缘会 100% 覆盖先绘制的碎片边缘。

**经代码核实为误报。** `piece_shape.dart` 中两条路径覆盖**不同的边**，不存在重合：

| 路径 | 构建函数 | 覆盖边 |
| :--- | :--- | :--- |
| `highlightPath` | `_buildHighlightPath()`（:185-204） | **Left + Top** |
| `shadowPath` | `_buildShadowPath()`（:207-226） | **Right + Bottom** |
| `path` | 完整轮廓 | 全部四边（用于 clip 与厚度层） |

同一碎片的 `highlightPath` 与 `shadowPath` 是互补的两条路径（注释亦明确「Top 边与 Left 边」/「Right 边与 Bottom 边」）。跨碎片看，A 的右边缘暗线与 B 的左边缘高光线**确实是同一条几何接缝**，但二者属于不同碎片、绘制于不同 `canvas.save/restore` 的独立变换中，**不存在「后绘制覆盖先绘制」的同路径覆盖关系**——它们是同一接缝上先画暗线、再画高光，视觉上是「接缝内外两侧各一条线」，这正是设计意图（135° 光照的立体层次）。

**影响**：该误报会误导实现者去引入 gm 建议的「高光降到 0.7px + 透明度降到 0x35」改动，而终稿 §1.3 与 §2.5 正确地**拒绝了这一改动**（「不改任何 Paint 颜色/透明度」「无白漆描边风险，少一个回归变量」）。**终稿的拒绝是正确的**，但 §1.3 分歧裁决表未记录该误报的性质，建议补注。

### 3.3 gm 2.1 的修复公式本身有反直觉错误（终稿已规避）

gm 建议：

```dart
_shadowOutlinePaint.strokeWidth = min(1.2, 1.0 / curScale);
```

当 `curScale = 0.21`（2×2 托盘）时：`min(1.2, 4.76) = 1.2`，屏幕宽度 = `1.2 × 0.21 = 0.25px`——**与改前的现状相同，并非 gm 所称的「保留原默认上限」意义上的正确**。gm 的公式在 `curScale < 1` 时确实避免了暴增，但代价是低难度托盘线宽维持在**几乎不可见**的状态。

**终稿的 `max(s, 1.0)` 口径更优**：在 `s ≤ 1` 时直接 `baseline / 1.0 = baseline`，与改前逐像素一致，且语义更清晰。这一条终稿处理正确。

### 3.4 gm 2.2 的修复公式有反转风险（终稿已规避）

gm 建议 `min(0.8, 0.8 / curScale)`：当 `curScale = 0.21` 时得 `0.8`，屏幕 = `0.168px`；当 `curScale = 4` 时得 `0.2`，屏幕 = `0.8px` ✓。但它**在 `curScale < 1` 时对局部值不做任何收窄**，与终稿「托盘态完全不变」的目标相比，终稿的 `0.8 / s` 更符合「屏幕恒定」的原始意图。两条路线的差异仅在 `s < 1` 区间，终稿选择更保守（不改现状），可取。

| 共识 | 终稿处理 |
| :--- | :--- |
| `curScale` 必须取组件 `scale.x`，禁用 `game.zoom`（ds P0-1 首要） | §2.2 代码 + 注释明确「禁止使用 `game.zoom`」 ✅ |
| 取消常驻绿框不破坏边缘筛选（三方核实一致） | §2.4 删除复辟赋值，理由记录完整 ✅ |
