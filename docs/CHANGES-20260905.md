## Content Studio 交付 SQLite3 算力缓存引擎与 OpenCV 图像物理质检 2026-09-05 19:57
- **变更背景**：
  - 用户反馈图库扫描时 Hash 计算耗时（万张需十几秒），若未打标保存直接退出，下次仍需全量重算；
  - 机器特征（Hash、分辨率、清晰度、死区等技术指标）不应混入 `tags.json`（`tags.json` 应专门留给运营人员打标保存）；
  - 需要引入图片适玩度与质量评分（大面积纯色/层次过少检测），且必须兼顾高性能与断点缓存，即使文件改名或移动也能零损耗自动继承。
- **架构实现与变更**：
  - **SQLite3 底层算力缓存引擎** (`studio/core/cache_db.py`):

    - `quality_cache` 表：以**内容 SHA-256 Hash 为唯一主键**绑定 OpenCV 物理质检得分、评级（S/A/B/C/F）、盲盒死区占比、智能四周裁剪建议等完整指标。即使图片在磁盘上被移动或重命名，凭借不变的 Hash 即可 100% 毫秒级直接复用历史评分；
    - 废弃对账：`prune_missing_files` 自动扫描清理磁盘已删除的陈旧路径。
  - **OpenCV 物理质检与四周裁剪评估引擎** (`studio/core/quality_evaluator.py`):
    - 针对 8x8 切片网格实现边缘/内部核心死区分离容忍算法（四周边框死区容忍，内部核心死区加权重罚）；
    - 集成色相信息熵（HSV Color Entropy）、Laplacian 方差清晰度与空间均匀度量化；
    - 智能四周 ROI 裁剪潜力搜索引擎：自动检测顶部天空/单边暗部死区，给出四周裁切与适玩度提分预测；

## 修复 Windows 下服务端口被多实例并发静默占用（SO_EXCLUSIVEADDRUSE 独占监听） 2026-09-05 19:15
- **原因分析**：
  - Python 标准库 `http.server.ThreadingHTTPServer`（底层继承自 `socketserver.TCPServer`）默认硬编码开启了 `allow_reuse_address = 1`（`SO_REUSEADDR`）；
  - 在 Linux/macOS 上，`SO_REUSEADDR` 仅用于复用处于 `TIME_WAIT` 状态的端口以加速重启，不会允许两个进程同时 bind 处于 LISTEN 状态的同一个端口；
  - 但在 Windows Winsock 底层实现中，`SO_REUSEADDR` 的语义存在严重陷阱——它允许不同的进程静默绑定到**完全相同的 IP 与端口**（端口劫持），导致两个命令行进程可以同时启动并在同一个端口监听，请求被随机分流或劫持，且没有任何端口已被占用的报错提示。
- **架构实现与变更**：
  - **定制 StudioServer 实现** (`studio/server.py`):
    - 自定义 `StudioServer` 类继承 `ThreadingHTTPServer`；
    - 在 Windows 下关闭 `allow_reuse_address = False`，并在 `server_bind` 阶段显式配置 Windows 专属的 `socket.SO_EXCLUSIVEADDRUSE = 1` 套接字选项，强制实施独占绑定；
    - 捕获 `OSError`（Windows `WinError 10048`），当端口被已有实例或其它进程占用时，立即向控制台与日志输出友好的错误提示，并建议使用 `--port` 参数切换端口，安全退出进程。
  - **自动化测试套件** (`studio/test_studio.py`):
    - 新增 `test_studio_server_prevents_port_reuse` 单元测试，自动分配动态端口并启动两个 Server 实例，断言第二个实例必然被拦截并抛出 `WinError 10048`。
- **验证结果**：
  - `python -m unittest studio/test_studio.py`: 20/20 单元测试通过；
  - 真实双命令行启动验证：第二个实例准确拦截并报错退出（`code 1`）。

## 实现基于文件内容 Hash 的防重导出与打标自动继承闭环系统 2026-09-05 18:52
- **变更背景**：
  - 以往以“文件相对路径”作为索引存在两大缺陷：文件一旦改名或移动，已有打标成果彻底丢失（路径断裂沦为孤儿死数据）；多批次导出（Main/Daily/Event/Collection）缺乏素材消耗记录，极易产生跨包重复导出；
  - 确立以「图片源目录 (Source Directory)」为唯一工作区锚点，实现库级完全自包含与环境迁移隔离；
  - 经对 25,428 张真实图库实测（8 线程 SHA-256 达 2,136 张/秒，3,727 MB/s），采用全量 SHA-256 结合 `(mtime, size)` 增量哈希缓存，既保证极高抗碰撞性又实现日常 0ms 秒开。
- **架构实现与变更**：
  - **设计规范** (`studio/docs/content-studio-hash-and-export-tracking-design.md`):
    - 编制完整的技术规范书，规范 `tags.json` 与 `exported.json` 的职责分离与数据契约。
  - **导出账本管理** (`studio/core/export_tracker.py`):

  - **扫描与哈希加速** (`studio/core/scanner.py`):

    - 在 `get_image_info` 与 `scan_image_infos` 中增加增量哈希机制：对比 `mtime` 和 `size`，命中直接复用，未变动文件 0ms 秒开，仅对新增/改动文件计算 SHA-256。
  - **改名/移动自动认领引擎** (`studio/core/tags_manager.py`):

- **变更背景**：
  - 此前 `studio/server.py` 使用 Python 标准库默认的 `HTTPServer`，为严格的单线程阻塞模型。在画廊图片加载、切换目录或快速滚动时，浏览器会并发发起大量缩略图请求（涉及图片解码、LANCZOS 高质量重采样与磁盘 I/O）；
  - 前端心跳检测 `/api/health`（原本超时设定为 2.5s）在单线程队列中排在耗时的缩略图处理后，导致请求被动超时，从而引发前端误报「服务端连接已断开」及离线横幅抖动。
- **修改文件**：
  - `studio/server.py`:
    - 将 `HTTPServer` 升级为标准库自带的 `ThreadingHTTPServer`，零依赖实现请求多线程并发响应；
    - 配置 `httpd.daemon_threads = True`，确保服务端在关闭退出时工作线程干净退出，避免后台挂起。
  - `studio/core/image_proc.py`:
    - 增加 `os` 和 `threading` 模块导入；
    - 缩略图生成落盘写入服务端缓存时，在临时缓存文件名中引入进程 ID 与线程 ID，杜绝 Windows 下多线程并发为同图或相邻图写入缓存时发生文件占用冲突与锁错误。
  - `studio/static/js/api.js`:
    - `checkHealth` 默认超时阈值从 2.5s 放宽至 4.0s，兼顾响应敏锐度与网络/计算峰值容忍度。
  - `studio/static/js/app.js`:
    - 心跳状态增加连续失败容错机制（`consecutiveFailures`）：连续 2 次检测失败才判定离线，彻底消除因个别瞬间高并发排队引起的离线误报与状态频闪；
    - `handleImageError` 增加 800ms 防抖控制，避免多张图片加载失败时并发轰炸发起重复无意义的心跳检测。
- **校验**：
  - `python -m unittest studio/test_studio.py`: 全部 8 项单元测试通过；
  - 本地并发请求压测验证：多线程并发 `/api/health` 畅通无阻，毫秒级即时响应。
