# JigsawFox Changes - 2026-09-11

## 12:00

### Feature: 素材发布台账（.publish）与无变化检测

- **背景**: publish 侧此前只有 stdout 打印，无任何留存；且无法判断"这次是否与上次发布内容一致"，容易重复发布同一批文件。
- **改动**:
  1. 新增 `scripts/publish/ledger.py`：文件级指纹（size+sha256）、变化清单 diff、`.publish/` 台账读写与滚动归档（保留最近 50 次）。
  2. 台账落在 **jigsaw-data 仓库的 `.publish/`**（放在 `release/` 之外，避免被 prepare 的整目录重建清掉），随 Step 5 的 `git push` 入库，天然持久化且可跨机共享，同时充当下次运行的变化检测基线。
     - `run.json` 进行中的运行记录；`latest.json` 上次已完成发布的完整快照；`history.ndjson` 审计留痕；`runs/<runId>.json` 详情归档。
  3. **双层指纹**解决"复制到 release/ 后内容被改过"的比对难题：`sourceFingerprint` 记录未被改动的输入源聚合摘要（用于归因），`publishedFiles` 记录真正上传的那棵树的逐文件哈希（用于判定远端是否真的会变）。
  4. `prepare` 新增变化检测与拦截：产物与上次完全一致且远端已同步时**中止**（退出码 3）；远端不一致/被清空时放行以补全量；`--force` 可强制继续。`all` 遇退出码 3 视为正常终止。
  5. `stage`/`release`/`promote` 各步结果写入运行记录，`promote` 成功后归档为 `latest.json` 并追加 history 一行。
  6. `scripts/publish/README.md` 新增 §7「发布台账与无变化检测」，并明确 **publish 侧不自动自增 `main.version`**（由 Studio 导出侧负责，publish 只校验与提示）。
- **校验**: 首次发布不拦截；无变化+远端已清空 -> 放行并提示补全；无变化+远端已同步 -> 拦截 rc=3；`--force` 放行 rc=0；篡改基线后正确报出 `+1 新增 / ~2 变更` 且 `sourceChanged=false` 归因正确。

## 11:40

### Fix: 素材发布版本基线改从已发布产物自身读取，移除独立基线文件

- **问题**: `main.version` 递增门禁依赖 `temp/publish_baseline.json` 这个外挂文件，它会随 `temp/` 清理而丢失，也无法跨机器共享。
- **根因**: `prepare` 会先清空 `jigsaw-data/release/` 再重建，导致作为基线的 `release/manifest.json` 被覆盖、无从读取。
- **修复**: `scripts/publish/publish.py` 新增 `_read_prev_main_version()`，在**清空目录之前**读取上一版产物；本地缺失时回落到远端 R2 生产区 manifest，取不到则按首次发布放行。删除 `temp/publish_baseline.json`。
- **效果**: 基线回归单一真源（`jigsaw-data/release/manifest.json` 已由 Step 5 提交入库），无需维护额外文件，天然持久化且可跨机共享。
- **校验**: 本地有上一版 -> 返回 2；本地缺失 + R2 空桶 -> 返回 None（首发布语义）；连续两次 `prepare` 产物 hash 完全一致（幂等）。
- **备注**: 同时确认 `Output` 已于 10:56 被重导，events/collections 的 zip 文件名改为带 `event-` / `collection-` 前缀的新命名，故模块 hash 变化属数据源变更而非脚本不确定。

  2. `scripts/publish/publish.py`：重写为 `prepare/stage/verify/release/promote/all/git/purge` 编排器，支持 `--dry-run`、`--force`、`--env stage|prod`；内置白名单拷贝（排除 `.git` 等隐藏项）、源文件数守卫、zip 存在性与 basename 冲突校验、`main.version` 递增门禁（首跑写基线后放行）。
  3. `scripts/publish/gitee_release.py`：新增，走 Gitee OpenAPI v5 做附件增量上传；修正 Gitee「release 不存在时返回 200 + 空体」的判定问题，附带 800MB 软告警与 1GB 上限提醒。
  4. `scripts/publish/verify_channels.py`：重写为 `--env stage|prod` 巡检，JSON 按 sha256 逐字节比对本地，图片与 zip 校验可达性，默认跳过 `cn=0` 通道，`--include-mirrors` 做三通道全量终检。
  5. `test/logic/jigsawdata_three_channel_verify_test.dart`：断言改为 v2 契约（`zipUrl` 必须相对、`zipUrls` 必须绝对），下载改走「首个可达候选」以贴合客户端回退顺序；修正 R2/Gitee/GitHub 基址缺失 `release/` 段导致的 404。
  6. `app_content.dart`：`defaultBootstrapUrls` 切换为 R2 主 + Gitee 备 + GitHub 备，均指向 `release/manifest.json`。
  7. `jigsaw-data` 仓库：新增 `.gitignore`（排除 `*.zip`），完成 v2 `release/` 结构首版提交与推送。

## 10:14

### BugFix: 首页 main 数据 tag 过滤后图片内容错误 (hash 残留问题)

- **问题**: syncWithRemote 全新关卡分支复用旧本地同名图片文件，不校验 hash。服务端 batch_002 图片更新后，客户端保留了旧版图片（18张：main:101~118），导致 tag 过滤后图片内容不匹配（如美食 tag 出现熊猫/鹦鹉）。
- **根因**: `main_content_pipeline.dart` 在全新关卡时仅检查 `localFile.exists()`，未校验文件 hash 是否与服务端一致。
- **修复**:
  1. `pubspec.yaml` 添加 `crypto: ^3.0.6` 依赖
  2. `main_content_pipeline.dart`:
     - `syncWithRemote` 全新关卡分支：本地存在同名旧图时，先 `fileSizeBytes` 快速筛查，不匹配则直接删除；若 `fileSizeBytes` 匹配（或无此字段），再走 sha256 严格校验。
     - `ensureLevelImageDownloaded` 懒下载：命中本地文件时同样先走 `fileSizeBytes` 比对，不匹配则删除旧图并重下载；无 `fileSizeBytes` 时保留原有行为。
     - 新增 `_sha256File` 辅助方法。
  3. `puzzle_level_item.dart`: 新增 `fileSizeBytes` 字段，兼容旧数据（null 安全）。`fromJson`/`toJson`/`copyWith` 均已支持。
- **效果**: 服务端后续修图/替换批次时，App 会自动清理旧图并重下载，防止图片残留错位。优先用 `fileSizeBytes`（毫秒级）做快速不匹配筛查，sha256 兜底，两者组合兼顾性能与可靠性。
- **校验**: `flutter test` 316 tests all passed; `flutter build windows --debug` 编译通过。
