# 首页关卡全网络化（内置 0 + 首启转圈初始化）可行性调研

- 日期：2026-09-03（v2 修订）
- 类型：技术调研 / 方案论证（**未改动任何代码**）
- 结论一句话：**可以做，而且动机充分；但首启转圈只应等待"最小可玩集"（元数据 + 首屏缩略图，约 3 MB / 2–5 秒），100 关原图走后台 + 懒落地，并补齐无网兜底、进度改 ID 寻址、难度字段三项工程。**
- 关联文档：`docs/network-level-lazy-download-plan-20260902.md`、`docs/puzzle-content-packaging-tool-design.md`、`docs/puzzle-content-storage-and-expansion-design.md`

## 1. 现状盘点（代码事实）

### 1.1 首页现在是什么

| 项 | 现状 | 位置 |

> 关键认知：首页当前"内置 100 关"的包体代价只有 2.44MB。> 关键认知：2.44 MB **不是**"内置 100 关"的真实成本，它只是 10 张 placeholder 循环出来的结果。真实内容接入后必须按高质量档位重算（见 1.3）。

### 1.2 网络内容系统已就绪，但首页没接

`ContentManager` 全链路已跑通，只是首页 Tab 未消费：

```
AppContent.init()
  → ContentManager.initialize()        本地缓存秒开
  → _backgroundSync() → syncAll()
      → ManifestRouter.resolveManifest()   manifest.json（主备轮询 + 磁盘缓存 + 无网兜底）
      → MainContentPipeline.syncWithRemote()  main.json（version 增量 Upsert）
      → ensureLevelImageDownloaded()        懒下载落 levels/main/<id>.webp
```

- `ManifestRouter`：多 URL 轮询，单 URL 4s 超时，失败降级磁盘缓存，再降级内置兜底清单（`manifest_router.dart:23-89`）
- `MainContentPipeline.syncWithRemote`：`remoteVersion > localVersion` 才拉，Append-Only Upsert（`main_content_pipeline.dart:112`）
- 打包工具已可产出 `main.json` / `manifest.json`（`scripts/packaging/`）
- **尚未落地**：manifest 仍指向局域网 `http://192.168.1.118/data/www/game/test/manifest.json`（`app_content.dart:41`、`scripts/setup_test_server.py:20`），生产 CDN 未就位

### 1.3 素材库规模与真实体积实测

`jigsaw_raw/` = 4832 张 1024×1024 PNG，共 **8.2 GB**，均值 1.72 MB/张（生成源，非分发格式）。

**高质量档位 —— 内置 / 分发应采用，对齐业务方 200k–600k 每张的预期**：

| 规格 | 单张均值 | 100 关合计 | 备注 |
|---|---|---|---|
| WebP q85 @1536 | 279 KB | **27.2 MB** | 高质量下限 |
| WebP q88 @1536 | 330 KB | 32.2 MB | 高质量中段 |
| WebP q82 @2048 | 326 KB | 31.8 MB | 2K 下限 |
| WebP q85 @2048 | 373 KB | 36.4 MB | 2K 推荐 |
| WebP q90 @2048 | 504 KB | **49.3 MB** | 高质量上限 |

**真实高质量内容 100 关 = 20–50 MB（中位约 28 MB），与业务方给出的 200k–600k × 100 完全吻合。**

**低质量档位 —— 仅作对照，不建议用于内置关卡**：

| 规格 | 单张均值 | 100 关合计 |
|---|---|---|
| PNG 原图 1024² | 1759 KB | 171.8 MB |
| WebP q82 @1024 | 164 KB | 16.0 MB |
| WebP q75 @1024 | 124 KB | 12.1 MB（v1 误用此值） |
| WebP q80 @768 | 94 KB | 9.2 MB |
| 缩略图 360² JPEG q80（现有 `grid` 档位） | 36 KB | **3.5 MB** |

> 现状素材源为 1024²；若要上 1536² / 2048²，须在生成侧（ComfyUI 流水线）直接产出目标分辨率，而非上采样。

**首启下载耗时推算**（100 关原图按中位 28 MB 计）：

| 下载内容 | 体积 | WiFi 5 MB/s | 4G 2 MB/s | 弱网 300 KB/s |
|---|---|---|---|---|
| manifest + main.json | ~50 KB | 瞬时 | 瞬时 | <1 s |
| + 100 张缩略图 | ~3.5 MB | <1 s | ~2 s | ~12 s |
| + 100 张原图（全量） | ~32 MB | ~6 s | ~16 s | **~110 s** |
| **首屏最小集**（元数据 + 前 12 张缩略图） | ~0.5 MB | 瞬时 | <1 s | ~2 s |

## 2. 核心判断：动机成立（v2 修正）

**v1 说"省包体动机不成立"是错的。按真实高质量档位，动机充分。**

| 理由 | 量化 |
|---|---|
| 100 关高质量内容常驻首包 | **20–50 MB**（q85@1536 27.2 MB → q90@2048 49.3 MB）。虽未触及 Google Play 200 MB / iOS 4 GB 上限，但对首包、更新包、低端机存储都是实打实的负担，且内容量每翻一倍就再涨一倍 |
| 素材库规模 | 4832 张 × 高质量档位 ≈ **1.3 GB**，不可能全内置，图库制必须走网络 |
| **内容可替换（业务方提出）** | 内置图一旦发现不合适（质量、版权、审美、投诉），**只能发版才能换**；网络化可在分钟内下线/替换。这是运营硬需求，也是网络化最刚性的理由 |
| 统一管线 | 首页是目前唯一不走 `ContentManager` 的模块，daily / events 已网络化 |
| 行业验证 | 业务方实测 4–5 款 500 万+ 下载量 jigsaw app，**首次打开均需初始化几秒到十几秒** —— 说明该品类用户对此已建立预期 |

**真正该问的问题不是"要不要网络化"，而是"首启那一刻，转圈要等到什么程度为止"。**

网络化值得买的五条收益：

1. **内容可运营热更**：换图、上新、调序不发包
2. **内容可撤回 / 替换**：内置图出问题只能发版；网络图可分钟级下线
3. **无限扩充**：4832 张素材库不可能全内置
4. **首包可控**：20–50 MB 从首包移到按需
5. **与 daily / events 统一到一套管线**（现在首页是唯一的孤岛）

所以问题不该问"能不能全网络化"，而该问"**首启那一刻，有多少内容必须已经在本地**"。

## 3. 负面影响清单（按严重度分级）

### P0 —— 会造成事故或数据损坏

| # | 问题 | 说明 |
|---|---|---|
| 1 | **首启强依赖网络** | 无网 / 服务器故障 / 域名被墙 / DNS 污染 → 首页空白，App 完全不可用。当前 manifest 指向局域网 IP，生产 CDN 未落地，风险成倍放大。**这是"内置 0"唯一真正致命的点** |
| 2 | **转圈没有上限 / 没有降级** | 转圈本身可接受（行业常态），**不可接受的是无上限、无超时、无兜底**。弱网下 32 MB 要 110 秒；必须做到"超时即放行 + 后台续下 + 重试入口" |
| 3 | **进度索引漂移** | 网络关卡顺序由服务端 `order` 决定，而 `updateLevelProgress` 用**数组下标**写入。运营改序 / 增删关 → 老用户进度错位到别的图上。切网络必须同步把写路径改为 canonical ID |
| 4 | **难度字段缺失** | `main.json` 现有 `{url, tags, order}`，没有 `difficulty/pieces`。首页是 25→225 片阶梯关卡制，走网络后无法表达，必须扩 schema（连 `PuzzleLevelItem` 一起加字段） |
| 5 | **换图会毁掉已有存档**（业务方提出"想换就能换"的另一面） | 玩家在 `main:042` 上有进度 / 成就 / 金币记录，运营把 042 换成另一张图 → 进度还在但图不对，成就与截图全部错乱。**必须设计替换语义**：换图 = 下线旧图（移入"我的拼图"保留可玩）+ 新增新 ID，而不是原地覆盖 |

### P1 —— 体验或成本明显受损

| # | 问题 | 说明 |
|---|---|---|
| 5 | **离线可玩范围缩小** | 已下载过的关卡离线仍可玩（落盘在 `levels/main/`），但"首次进入某关必须联网"。对比 Magic Jigsaw Puzzles 商店页直接把 "**Offline puzzle game**" 当卖点——差距在首次体验，不在长期。可通过"常用关卡预缓存"缩小差距 |
| 6 | **CDN 成本随 DAU 线性增长** | Google 官方案例：Cookie Run 原用自建 CDN 分发 2.5 GB 资源，改用 Play Asset Delivery 后 CDN 费用降 **84%（年省 20 万美元）**、D14 留存提升。用自建 CDN 扛"所有人首启必下"是明确反模式 |
| 7 | **冷启动回归复杂度 ×3** | 需覆盖：无网 / 超时 / 部分失败 / 断点续传 / 校验 / 重试 / 版本回滚 / 灰度开关 |
| 8 | **商店审核与合规** | iOS 审核常在弱网或无网环境下验证基本功能；Google Play 要求披露下载体积；国内渠道需明示流量消耗 |
| 9 | **版本原子性** | manifest 更新到一半、某张图 404、CDN 缓存不一致 → 半新半旧的脏状态，比全旧更糟 |

### P2 —— 可控但必须处理

| # | 问题 | 缓解 |
|---|---|---|
| 10 | 磁盘无 LRU | 现有管线无淘汰策略，100 关原图+缩略 ≈ 20 MB 起步。后续按 `mtime` 淘汰最旧 20% |
| 11 | **老用户存档迁移（好消息）** | 只要服务端文件命名为 `001.webp` … `100.webp`，canonical ID 就是 `main:001`…`main:100`，**与现有存档天然兼容**；若沿用 `Landscapes_0000_2455645211_1024x1024.webp`，`order` 提取会取到 `0000`，且**全部老存档作废**。命名规则必须现在冻结 |
| 12 | 首启请求并发放大 | `syncAll` 用 `Future.wait` 并发拉 main/events/daily，首页再加 100 关会放大瞬时压力，需引入 `EngineTaskQueue` 单飞限流 |

## 4. 主流同类游戏对比

### 4.1 头部拼图产品

| 产品 | 首包体积 | 内置内容 | 网络策略 |
|---|---|---|---|
| **Magic Jigsaw Puzzles** (ZiMAD) | APK 118–146 MB；Microsoft Store 223 MB | 内置大图库，40000+ HD，**主打离线可玩** | 每日免费 1 张 + 主题 pack 按需下载；账号保存已下载 pack，可恢复误删 |
| **Jigsaw Puzzle** (MobilityWare) | — | 20000+ 图 | 每日免费 + Puzzle Packs 下载包（金币/积分兑换），每周上新 |
| Flutter 商业模板（Codecanyon 同类） | 小 | 目录全内置 | **No backend, no Firebase**，JSON 内置，明确以「全离线」为卖点 |
| **本项目现状** | 首页仅 2.44 MB（假数据） | 100 关 placeholder，真实内容未接入 | daily / events 已网络化，**home 仍是孤岛** |

### 4.1b 业务方实测观察（v2 新增，权重高于文献）

> 实测 4–5 款下载量 500 万以上的 jigsaw 类 App：**首次打开均需初始化几秒到十几秒**，之后才进入首页。

这条实测推翻了 v1 的两个推断：

1. **"首启转圈"在该品类是可接受的用户预期**，不是缺陷。v1 引用的通用"10 秒红线"来自手游大盘经验，对拼图这类**内容型、单次会话长**的品类不适用。
2. **但"几秒到十几秒"恰恰说明它们没有在首启下载全部原图。** 反推一下：

| 网络条件 | 3 s 能下 | 15 s 能下 |
|---|---|---|
| WiFi 5 MB/s | 15 MB | 75 MB |
| 4G 2 MB/s | 6 MB | 30 MB |
| 弱网 300 KB/s | 0.9 MB | 4.5 MB |

100 关高质量原图 = 28 MB：WiFi 需 6 s、4G 需 16 s、弱网需 110 s。若真的"首启全量阻塞"，弱网用户要等近两分钟，不可能只做到"几秒到十几秒"。

**所以最合理的解释是：那些 App 首启只下载了元数据 + 缩略图（3–5 MB），原图走懒落地。** 这与本方案 5 的推荐一致，而不是与"内置 0 + 全量阻塞"一致。

### 4.2 平台官方指引

| 平台 | 建议 |
|---|---|
| **Apple** | base installation 要提供足够内容供玩家评估游戏；首次下载控制在 30 分钟内；优先用 **On-Demand Resources**（initial install tags / prefetch tags）或 **Background Assets**，而非"纯 in-app 二次下载" |
| **Google Play PAD** | 三档：`install-time`（随安装下发，启动即可用，计入商店体积）、`fast-follow`（**装完自动下、不阻塞进 App、不计商店体积**）、`on-demand`（运行时按需）。全部由 Google 托管，**免自建 CDN** |
| 行业留存经验 | 首启下载 <10 s；"**Do Not Download Everything at Once**"；分块渐进下载；进度条 + 动画 + 分段文案可重置用户心理时钟。注：该经验对拼图品类应适度放宽，但"分块渐进"仍然成立 |

## 5. 推荐方案：内置 0 + 首启最小集 + 后台渐进（v2）

v2 尊重"内置 0"的决策（动机见 §2），只把**首启阻塞的边界**收紧。

```
首启转圈（有上限，目标 2–5 s，硬上限 10 s）
  ├─ 1. manifest.json            ~2 KB
  ├─ 2. main.json                ~50 KB
  └─ 3. 前 12 张缩略图（首屏 2 行） ~0.5 MB
        ↓ 达到任一条件立即放行进首页：全部就绪 / 超过软超时
        ↓
┌─ 进首页：首屏 12 关有图可点，点击即玩（原图可能还在下，见下）
│
├─ 后台队列（EngineTaskQueue 单飞 + 限并发 2–4）
│    · 剩余 88 张缩略图           ~3 MB
│    · 前 20 关原图（预温）        ~5.6 MB
│    · 滚动可视的原图（懒落地）     按需
│
├─ 弱网/失败降级
│    · 硬超时（10 s）→ 直接进首页，卡片显示占位 + 重试按钮
│    · 无网 → 首页显示"需要联网首次加载"+ 重试入口，绝不空白
│
└─ 二次启动：本地缓存直出，syncAll 只拉增量（version 未变则跳过）
```

**为什么首启只等这 0.5 MB 而不是 32 MB**：

| 方案 | WiFi | 4G | 弱网 | 无网 |
|---|---|---|---|---|
| 等全部原图 32 MB | 6 s | 16 s | **110 s** | 卡死 |
| 等全部缩略图 3.5 MB | <1 s | 2 s | 12 s | 卡死 |
| **等最小集 0.5 MB** | 瞬时 | <1 s | 2 s | **2 s 后报错重试** |

三者都落在"几秒到十几秒"的品类常态内，但只有最小集方案在弱网/无网下不会崩。

**收益**：内容全网络化（可换、可扩、可撤）；首启等待落在行业常态区间且**有上界**；弱网/无网可优雅降级；老存档零迁移（命名对齐前提下）。

### 5.1 必须补齐的 9 项工程保障

| # | 项 | 具体做法 |
|---|---|---|
| 1 | **首启只等最小集** | manifest + main.json + 首屏 12 张缩略图（~0.5 MB）。原图全部后台补 |
| 2 | **双重超时** | 软超时 5 s（有部分数据就放行）+ 硬超时 10 s（无条件放行）。现有 `ManifestRouter` 是单 URL 4 s 一刀切，需改分级：元数据 3 s / 缩略图 8 s / 原图 20 s |
| 3 | **无网兜底页** | 重试 / 查看已下载 / 退出，三选一。**禁止空白首页** |
| 4 | **进度反馈** | 百分比 + 分段文案（"正在获取图库… 12/100"）+ 动画，不要只有转圈 |
| 5 | **完整性校验** | `sha1` + `bytes` 清单；单图失败独立重试，不影响整体放行 |
| 6 | **灰度开关** | manifest 下发 `homeStrategy`（`network` / `builtin`），线上异常可一键回退 |
| 7 | **换图语义** | 见 P0-5：**下线旧图 + 新增新 ID**，禁止原地覆盖。旧图移入"我的拼图"保留可玩与存档 |
| 8 | **优先平台分发** | Android 走 PAD `fast-follow`（装完自动下、不阻塞进 App、不计商店体积、零 CDN 费）；iOS 走 ODR / Background Assets。自建 CDN 作为兜底与国内渠道方案 |
| 9 | **先落地生产 CDN** | 现在 manifest 还指向 `192.168.1.118` 局域网地址，这是当前最大的单点风险 |

### 5.2 可选的加强项：内置极简 starter（若后续想消除无网死角）

若未来评估认为"无网完全不能玩"不可接受，可补内置 8–12 关 starter（q85@1536 ≈ 2.2–3.3 MB）：成本极低，仅作为无网兜底与首帧占位，不参与运营。这是**后置可选项**，不阻塞当前网络化方案。

## 6. `main.json` 需要扩展的字段

现状只有 `{url, tags, order}`，无法支撑首页关卡制：

```json
{
  "version": 122,
  "levels": [
    {
      "url": "https://cdn.example.com/puzzle/main/042.webp",
      "order": 42,
      "tags": ["Landscapes"],
      "pieces": 64,
      "addedAt": "2026-09-01T00:00:00+08:00",
      "sha1": "6f3a...",
      "bytes": 126976
    }
  ]
}
```

| 字段 | 必要性 | 说明 |
|---|---|---|
| `pieces` | **必须** | 替代硬编码阶梯难度；`PuzzleLevelItem` 与 `LevelItem` 需同步加字段 |
| `sha1` / `bytes` | 建议 | 断点续传、完整性校验、下载进度百分比 |
| `status` / `replacedBy` | **必须**（若支持换图） | `status: active / retired`；下线的图 `retired` 并指向 `replacedBy`，客户端保留旧图可玩（P0-5）。**禁止原地替换 url** |
| 文件命名 `NNN.webp` | **必须** | 保证 canonical ID = `main:NNN`，与现有存档对齐（见 P2-11） |

> 换图正确姿势：`main:042` 要换 → 标记 `042` 为 `retired`（旧图保留在本地，玩家仍可在"我的拼图"继续），**新增** `main:101` 承接新图并调 `order`。进度、成就、金币记录全部不丢。

## 9. 三句话总结（v2）

1. **可以做。** 真实高质量内容 100 关 20–50 MB、素材库 4832 张无法全内置、内容需可替换 —— 网络化动机充分，v1 的"包体不是瓶颈"结论作废。
