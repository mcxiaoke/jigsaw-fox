## [2026-08-31 15:54 GMT+8] 任务调度改为 tag 轮转交错 + 外部资料技术参数核实

**修改文件**：`scripts/comfyui_batch_gen.py`、`scripts/my_comfyui_batch_gen.py`

**问题（用户指出，实测印证）**：原调度按 tag 顺序跑完一个再跑下一个，中断时后面的 tag 颗粒无收。停止时实测 1467 张的分布为：Animals/Pets/Nature/Landscapes/Flowers/Ocean 各 216 张、Birds 171 张，而 **Cities 及之后 14 个 tag 全部为 0 张**。

**改动**：
- 新增 `--batch-per-tag`（默认 4）：jobs 生成后按 `(index // batch, tag_order, index)` 重排，实现 tag 交错调度 —— 每个 tag 先各出一批（默认 4 张），21 个 tag 走完算一个 round，再回到开头继续下一批；
- **job key 保持不变**（仍为 `{tag}:{index:04d}`），因此已有的 1460 张进度完全兼容，重跑只补未完成的，且零进度 tag 会立即开始出图，无需重跑已完成的；
- `--batch-per-tag 0` 可退回旧的"跑完一个 tag 再跑下一个"行为；
- 两个脚本同步改造（`comfyui_batch_gen.py` 与 `my_comfyui_batch_gen.py`），均 `py_compile` 通过；dry-run 验证顺序为 Animals×4 → Pets×4 → Nature×4 → Landscapes×4 …

**外部资料核实（用户提醒"别人的资料不等于全对"，已逐条核查）**：

| 资料主张 | 核实结论 |
|---------|---------|
| Turbo 模型 CFG 应设 1.5~2.5 | ❌ **不采纳**。官方 HF model card 与 Replicate 部署均为 `guidance_scale=0.0`；官方源码 `src/config/inference.py` 中 `DEFAULT_GUIDANCE_SCALE = 0.0`，明确"DMDR 后训练已优化到无需引导"（ComfyUI 中 CFG=1.0 即等价无引导）。更关键：源码说明 CFG>0 时每步需 **2 次 forward pass**（条件+无条件），**速度翻倍**——我们 13s/张建立在单 forward 上，改 2.0 会升至 25s+，4536 张从 18.5h 膨胀到 30h+。实践派自己也警告"提高 CFG 会劣化蒸馏模型输出" |
| 步数 6~10 | ✅ 采纳（当前 9 步，在官方推荐的 9 步 / 8 NFE 上） |
| 用反向词拦截 "jigsaw puzzle lines" | ⚠️ **对本项目无效**。CFG≈1 时负向提示词不参与计算（已在 v3.0 库中改为正向规避：prompt 里绝不出现 puzzle 相关词） |
| 竖屏 896×1152（3:4） | ❌ 不采纳。游戏仅支持 1:1 / 2:3 / 3:2，3:4 需额外裁切 |
| 20 类"视觉锚点"清单（如霓虹招牌、马卡龙、海龟壳花纹） | ✅ **有价值**，属设计经验非技术参数，待用户评判 v3.0 出图后决定是否融入 subject |

**参考**：同批搜索中 CSDN 某文主张"CFG 7.5、768×768"系把 SD1.5 参数套用于 Z-Image，与官方 1024×1024 / CFG 0.0 完全矛盾，属站群文不予采信。

## [2026-08-31 08:43 GMT+8] prompt 库 v3.0 重构（主体突出 / 分区构图 / 中尺度细节 / 鲜艳色彩 / 风格维度）

**新增文件**：`scripts/my_prompt_library.json`（v3.0）、`scripts/my_comfyui_batch_gen.py`（脚本副本）
**不动文件**：`scripts/comfyui_batch_gen.py`、`scripts/jigsaw_prompt_library.json`（正在跑批中，保持原样）

**重构背景（用户对 v2.0 出图的三条反馈）**：

| 现象 | v2.0 prompt 的方向性错误 |
|------|------------------------|
| 主体不突出 | 通篇只有 `dense texture / busy composition / filled frame`，**从未要求一个清晰主体** |
| 细节过多、元素冲突（一张图四只猫） | 单条 subject 并列堆 6~8 个名词（"moss, ferns, orchids, lianas, mushrooms, roots..."），模型理解为"全部塞进去"→ 杂乱 |
| 色彩不够鲜艳 | `atmosphere` 维度混入 `muted natural tones`、`cool blue-green tint`、`soft pastel` 等**主动降低饱和**的词 |

**v3.0 改动（采用用户提供的 gpt-image-2 提示词模板）**：
- **subject 重写为「主体 + 四象限分区」结构**：252 条全部改为 `one <X> as the clear central subject, with <元素> in the lower left, <元素> in the upper right, <元素> along the bottom edge, and <背景> behind` —— 既保证四象限都有内容（防死区），又把次要元素控制在 3~4 个（防堆砌冲突）；
- **quality_suffix 全面改写**：删除 `dense visual texture / busy composition / fine micro texture`（"细节过多"的元凶），改为 `clean uncluttered composition with one clear focal point, medium-scale readable details instead of microscopic texture, vibrant saturated colors, strong visual hierarchy, meaningful detail continuing into all four edges and corners`；
- **新增 `style` 修饰维度**（8 种：cinematic storybook realism / paper-cut collage / watercolor ink / isometric diorama / retro-futurist screen print / classical oil / 3D render / art nouveau）—— v2.0 完全没有风格维度，这是出图"不够像成品插画"的重要原因；
- **atmosphere 全部换为高饱和**：`rich saturated color grading`、`vivid jewel-tone colors`、`high contrast bold colors` 等，删除所有 muted/pastel 低饱和词；
- **精简冗余 extra**：13 个 tag 的 extra 与 subject 主体描述重复，清空；保留 Animals/Pets/Birds（强调"单只"防多主体）、Ocean/Space/Abstract（防死区与重复歧义）、People（防肖像）、Cartoon（防扁平背景）8 个有实际约束价值的；
- **脚本副本适配**：`my_comfyui_batch_gen.py` 默认读取 `my_prompt_library.json`，`build_jobs` 修饰词槽位改为 `style/detail/atmosphere` 三者可选（向后兼容 v2.0 库的 detail）。

**验证**：两脚本 `py_compile` 通过；`--list-tags` 均 2280 张；dry-run 对比确认新 prompt 已含主体/分区/风格/鲜艳色调四项改进。**尚未真机出图验证视觉效果**，需跑小批量对比后决定是否替换 v2.0 产出。

## [2026-08-31 08:20 GMT+8] 批量生成脚本新增长跑稳定性防护（定时硬重置 + 驱动卡死检测）

**修改文件**：`scripts/comfyui_batch_gen.py`、`docs/comfyui-batch-generation-guide.md`

**背景（真实故障）**：`--rounds 18` 连续跑至第 1550 张（约 7 小时）时 CUDA 驱动卡死，整机假死需强制关机。事后检查 `C:/Home/Temp/JigsawOutput/_progress.json`：**done=1550、failed=0，7 个 tag 各 216 张（12 subject × 18 轮）已完整产出，Cities 进行到 44/216** —— 断点续跑机制在真实故障下验证有效，无一张丢失。

**改动内容**：
- **定时硬重置** `--hard-reset-minutes`（默认 10）：每 N 分钟调用 `/free {unload_models: true, free_memory: true}`，主动清空显存碎片与驻留模型，让 GPU 周期性复位，对抗长跑碎片累积导致的驱动挂起。代价可忽略（每次释放后下一张重载 +7s，按 10 分钟 37 张折算约 0.2s/张）；
- **卡死检测** `--stuck-timeout`（默认 90s）：新增 `wait_for_image()` 替代原来的固定轮询 —— 单张超过阈值未出图时用 `/system_stats` 短超时探活，驱动挂起时立即抛 `ComfyStuck` 而非干等 240s；卡死图**不重试**（驱动级挂起重试无意义且有风险）；
- **连续卡死中止** `--max-stuck`（默认 3）：连续 N 张判定卡死后主动落盘进度并退出，避免整机假死时连进度都保不住；
- `ComfyClient` 改造：`_request` 支持单次调用 `timeout` 覆盖，新增 `alive()` 探活方法，新增 `ComfyStuck` 异常类型；
- 文档 §7.5 参数表补齐三个新参数（`--sec-per-image` 默认值同步修正为 16s），新增 **§7.7 长跑稳定性**章节：记录 1550 张卡死的实测教训、三层防护机制、四项降低卡死概率的措施（移除第三方 custom nodes / 不并行吃显存程序 / 中途检查单张耗时 / 调大释放频率），并明确"驱动级硬卡死软件无法自救，脚本只做预防 + 早止损"这一边界。

**防护边界说明**：驱动硬卡死属于 WDDM/TDR 层面，脚本无法自救；能做的是降低发生概率（定时释放、移除泄漏源）与保住进度（探活早停、进度落盘）。真卡死后流程为：重启机器 → 启动 ComfyUI → 重跑同一条命令续跑。

**验证**：`py_compile` 通过；`--rounds 1` dry-run 正常（252 jobs、节点探测 4/8/6/10）。尚未在长跑中实测 hard reset 触发。
