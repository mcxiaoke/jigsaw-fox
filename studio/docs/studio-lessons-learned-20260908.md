> 目的：把一次次的「踩坑 → 修复」抽象成**下次能直接复用**的判断规则，避免同一个坑换皮重来。

## 零、一句话版本

> 这个工作台出过的问题，**八成不是算法问题，而是「两端口径不一致」和「改动只做了一半」**。
> 剩下两成里，一半是「静默失败」，一半是「优化选错了杠杆」。

下面按这个判断展开。

---

## 一、最高频的一类 Bug：口径不一致（两端各改一半）

这是本轮出现次数最多、危害最大的一类——**因为它不报错，只是结果悄悄不对**。

| 案例 | 现象 | 根因 | 通用防御 |
|---|---|---|---|
| 排序静默退化 | 手动拖拽的顺序在产物上不对 | `/api/export/preview` 用 `Path(src)`，而 `/api/scan` 和 `build_manual_order` 用 `Path(src).resolve()`。srcDir 为相对路径 / 含 `..` / 盘符大小写不同时，键匹配失败，**静默退化成扫描字典序且无告警** | 凡涉及路径拼接比较的模块，统一 `.resolve()` + posix 斜杠；能退化成默认值的地方必须打日志 |
| `✕` 剔除的图照样导出 | 预览 8 张、实际导出 10 张且序号错位 | 前端只从 `previewOrdered` 数组里删了，没告诉后端；后端按全量扫描导出，被删的图拿到兜底 rank 排到末尾 | **「前端看不到」不等于「后端不处理」**。任何前端的删减/筛选，都要有显式契约字段传到后端（本例：`excludedPaths`，且按小写 posix 相对路径比对） |
| 未分类素材永不标待复核 | `conf=1.0` 的未打标素材 `review_required` 恒为 False | `("others" in tags)` 对规范形式 `"Others"` 永远为假 | 字符串常量**单点定义**（`OTHERS_TAG`），禁止字面量散落；集合成员判断优先用常量而非手写大小写 |
| 预检统计键名漂移 | 导出预检 `stats.tags` 键是小写 `others` 而非 `Others` | 兜底标签在服务端另一处硬编码 `["others"]` | 同上：兜底值也必须走常量 |

**可复用规则：**

1. **任何「一边改了另一边没改」的改动，一律视为未完成。** 提交前自问：后端有了，前端有没有？预检有了，导出有没有？写路径有了，读路径有没有？
2. **能静默退化的分支必须打点。** `root` 匹配不上就退化成字典序——这类"兜底"是 bug 温床，宁可 `logger.warning`。
3. **常量收敛到单一事实源**：`OTHERS_TAG`、`DEFAULT_LONG_TARGET`、`AUTO_FAMILIES` 都由一处定义，其余 `import`。

## 二、第二类：只做了一半的改动（死代码与漏字段）

| 案例 | 发现 |
|---|---|
| `moveExportItem` / `removeFromPreview` 是从未被模板引用的死代码 | 函数写好了但 HTML 里没绑，功能等于没做。**写完函数不等于交付功能**——要确认它在 UI 上真的可达 |
| `merge_scanned_images` 的字段白名单漏加 `long_side` / `too_small_long` | 新增字段时，所有"字段白名单 / 记录补齐 / 序列化"的地方都要同步扫一遍。这类白名单是隐式契约，编译器不会提醒 |
| `persistConfig` 没暴露到 `return` 块 | 模板里 `@change` 静默失效。Vue 组合式 API 的 `return` 块就是导出清单，漏了没有任何报错 |
| `.btn` 基础类没设 `color`，深色工具栏上白底白字 | 组件基础样式要在最坏背景上验证，不能只在当前用的地方看着对 |

**可复用规则：**

- **新增字段 checklist**：数据结构 → 白名单/补齐 → 序列化(slim) → 前端消费 → 单元测试，五处一起改。
- **新增函数 checklist**：定义 → 模板/调用点绑定 → 实机点一次 → 断言可见效果。
- Vue `setup()` 的 `return` 块改动后，用一次页面点击验证，别只看 `node --check`。

## 三、第三类：优化选错杠杆

### 3.1 转码提速：换库 vs 并行

实测（本机 8 核 16 线程，webp q70，16 张 309MB）：

```
Pillow m6 顺序（原实现）      86.9s    1x
Pillow m6 进程池 x8          19.0s    4.6x
vips effort=6 进程池 x8      14.2s    6.1x   ← 引入外部依赖
NConvert 单进程                ~2.9s/张  ~2x
pyvips 顺序（内部线程）        69.2s    1.3x
```

**教训**：单张编码换库（vips/NConvert/pyvips）只有 20~50% 收益，还得背一个外部二进制依赖；**数量级收益来自「多图并行」**——XnConvert 50 张 14s 同为此理。先做免费的进程池并行，再谈换库。

落地形态（已在 `image_proc.convert_images_parallel`）：

- worker 必须是**模块级函数**（Windows spawn 需要可 pickle）；
- 池不可用时**自动回退串行**，绝不中断主流程；
- 并行产物与串行必须**逐字节一致**（去除时间戳字段后比对），否则就是引入了新 bug。

### 3.2 请求体瘦身：改序列化比改算法便宜

3000 张的预检请求 2.1MB → 580KB（-72.6%），只做了两件事：

- `JSON.stringify` 去掉缩进（缩进让体积近乎翻倍）；
- `buildSlimRecords()` 只回传 `path/file/hash/tags/exported` 五字段，不回传 width/height/quality/size。

**教训**：大规模数据先看「传了多少」，再看「算了多少」。

### 3.3 刷新用轻量端点，不用全量重扫

质检完成后原本 `finalizeQualityJob` 调 `/api/scan` 全量重扫来刷新分数——1138 张要 `os.stat` × 1138 + 读哈希缓存 + 加载账本 + 重复检测，虽然缓存命中只有 0.12s，但本质是浪费：**质检只改了 SQLite 里的分数，不需要碰文件系统**。

改为新增 `GET /api/quality/scores`：一条 `file_cache LEFT JOIN quality_cache` 出结果，前端 merge 到已有 records。

**教训**：**按「改了什么」选择刷新粒度**。改 SQLite 就查 SQLite，别顺手 rescan 文件系统。

### 3.4 前端渲染：先减负，再虚拟化

- 缩略图尺寸分桶（240/360/480/640/800）+ 后端 ETag/`max-age=86400, immutable`：提高缓存命中，省的是网络与解码；
- `.og-card` `content-visibility:auto` + `contain-intrinsic-size`：视口外跳过布局绘制，**但不减少 DOM 节点**——25k 张仍是 2.5 万节点，虚拟滚动仍是未解债。

**教训**：分清两个问题——「渲染慢」（`content-visibility` 可解）和「节点太多」（只能虚拟化）。且虚拟化与 SortableJS 拖拽冲突（拖拽需要真实 DOM）；`↑/↓` 操作数组下标则天然兼容。

## 四、架构层面的正确取舍（值得延续的）

### 4.1 进度感知：同步执行 + 只读轮询

导出**仍在原 POST 请求线程内同步跑完**，不引入后台线程 / SSE / 任务生命周期；前端并发轮询只读状态接口拿进度。

- 收益：执行模型零改动，风险面最小；
- 可靠性底线：**无 `clientTaskId` 的请求走原代码路径，行为零变化**（既有单测直调不受影响）；
- 收尾用**幂等 `finalize()`**：POST 结果与轮询谁先到终态谁收尾，后到者忽略；
- 最坏情况 = 回到旧行为（轮询 404/网络错误静默停止，靠 POST 自身结果兜底）。

**可复用模式**：观测性改造优先选「加一条只读旁路」，而不是「重写执行模型」。

### 4.2 试导出：同一套代码 + `read_only` 开关，而不是复制一份逻辑

`ExportsLedger` / `StudioWorkspace` 加 `read_only` 参数；`BaseExporter._write_root()` 把构建根重定向到 `outDir/_trial_{ts}` 并连 `self.out_p` 一起改掉，使 copy / manifest / 文件清单天然落进试导出目录；`_commit()` 掐断写账本与 release 镜像。

三个关键点：

1. **读状态仍从 release 状态源读**，所以试导出分配到的 version / startOrder 与正式导出完全一致——这是"预演"有意义的前提；
2. `_trial_meta/` 三件套（`source_map.json` / `ledger_delta.json` / `trial.log`）让试导出**自包含可检**；
3. 测试用**快照对比**证明零污染：试导出前后 `.studio` 存在性 / 内容 / mtime 均不变，且正式导出对照组**确实**会写——只测"没写"是不够的，要证明"对照组会写"，否则断言可能是假阳性。

**已知缺口**：绕过前端直接调 API 无二次确认（纯前端防呆的固有边界，已记录未修）。

### 4.3 质检异步化：与导出相反的选择

质检**改成了真后台任务**（子批 50 → 落库 → 进度回写）。原因是两者性质不同：质检可断点续算、可取消、量大且用户不需要立刻看到结果；导出需要明确的成功/失败产物与账本写入。

- 子批落库让**取消/崩溃天然断点续算**（下次只算 `get_unscored_items`）；
- 协作式取消：只置 `cancel=True`，worker 在子批边界检查；
- `localStorage["activeQualityTask"]` + `onMounted` 的 `resumeQualityJob()` 实现**刷新后自动重连**；
- 任务丢失（服务重启/超时）不报错，按成功恢复——从 SQLite 装配已落库结果。

**教训**：不要一刀切「全部异步」或「全部同步」，按「是否需要明确的终态产物」决定。

### 4.4 「不变量」优于「到处特判」

无标签素材的 tags 一律落成规范形式 `["Others"]`（绝非空数组或小写 `others`）。于是「是否未分类」在任何位置都等价于 `tags.includes(OTHERS)`——筛选、统计、待复核判定**全部坍缩成一个判定**，且前端后端同口径。

**可复用模式**：与其在十个地方写兼容分支，不如**在数据入口强制归一化，然后让不变量恒成立**。

## 五、UI 与交互层的坑

| 坑 | 表现 | 解法 |
|---|---|---|
| 一闪而过的 toast 承载校验错误 | 点导出"没反应" | 新增 `exportError` + **持久红条**，文案按「少了什么 → 在哪里补」两句式写清，修正后自动消失 |
| 大屏空间浪费 | 导出工作台仅 880px | `.export-view` 提到 `max-width:1920px`；`.export-body` 用 `flex:1 + min-height:0` 精确填满，消除底部留白 |
| 两个分布图互相挤压 | 标签分布压扁目录分布 | 各自**独立归一化刻度**（`distMaxTags` / `distMaxDirs`） |
| 完成态统计消失 | 导出完跳第④步，统计面板没了 | 新增 `exportDone`，**停留第③步预览视图**，底部只留「关闭」 |
| 原生图片拖拽抢事件 | SortableJS 拖拽失效 | `.og-thumb` 加 `draggable="false"` + `pointer-events:none` |
| 大列表拖拽卡顿 | 无法精确调整顺序 | 补 `↑ / ↓ / ✕` 按钮兜底——**操作数组下标，与 DOM 无关** |
| 竖图 overlay 百分比错位 | 裁切框画歪 | 根因是 CSS `inline-block` + `max-height:100%` 在 flex 容器里的**循环高度依赖**；改由 JS `syncViewerImg()` 同步 wrapper 到 img 实际渲染尺寸 |
| Cropper 坐标不对 | 裁切框偏移 | `getData()` 返回容器缩放坐标，必须 `getData(true)` 拿**原图像素坐标** |
| 深色背景上看不清按钮 | 白底白字 | `.btn` 基础类显式 `color: var(--text-main)`；新增 `.btn.warn` 让"标记待复核"在非绿色态可见 |
| 黑色背景图片无边界 | 分不清图在哪 | `.viewer-dialog` 背景 `#090d16` → `#3a3a3a` 中灰 |

## 六、可观测性：先补齐，再谈优化

一天的变更里有四次集中在日志上（B1→B5），顺序值得借鉴：

1. **B1/B4 导出链路落盘 + 静默 catch 改 warning**：把 `except: pass` / `return False` 全改成 `logger.warning/error`（含文件路径与根因）。这一步的收益是**把隐藏问题变可见**——很多"莫名不对"其实是静默异常。
2. **B2/B3 关键进度点打点**：扫描、质检、标签保存、账本追加、缩略图缓存各加 `[模块] 阶段: 数量` 日志。
3. **B5 按日期命名** `temp/studio-YYYYMMDD.log`（不做大小轮转，够用）。
4. **前端补齐**：`logger.js` 接管 console + 环形缓冲 + 浮动面板，7 处用户可见错误的 catch 接 `console.error`。

两条值得记住的细节：

- `core/image_proc.py` 的 logger 变量名是 `_logger` 不是 `logger`——改动时插错位置会 `NameError`。**统一命名比记住例外更划算**。
- 高频端点（`/api/thumb`、`/static/`、`/api/health`）在 `log_message` 里**降为 DEBUG**，否则日志会被心跳和缩略图淹没。

## 七、工程习惯（这套流程本身是有效的，保持）

- **设计文档 → 实施 → CHANGES**：每个非平凡改动都有设计文档（`*-design-20260908.md`），CHANGES 里写明「承接哪份设计」，可回溯。
- **备份先行**：改动前把未提交文件复制到 `temp/backups/<主题>-<时间戳>/`，不依赖 git 兜底。
- **分层验证**：`py_compile` / `node --check` → 单元测试（38→46→51 项）→ `curl` 端到端 → Playwright 实机。四层各自拦不同类别的问题，缺一层就会漏。
- **回归脚本沉淀**：`temp/studio_debug/` 下 `probe_preview.py`、`ui_probe.py`、`drag_probe.py`、`verify_fixes.py` 等可复跑探针——比"当时手工点过"可靠得多。
- **「未处理（需单独拍板）」清单**：每轮收尾明确列出未做项与理由，避免隐式技术债。

## 八、当前技术债与已发现的口径漂移

复核源码时发现以下几处不一致（均为**文档/默认值滞后于代码**，非新引入故障，但建议处理）：

| 项 | 现状 | 建议 |
|---|---|---|
| 前端 `startOrder` 初值 101 | `exportConfig.startOrder` 初值 101 且总随 payload 显式提交；后端 `MainExporter` 默认已是 1。`loadExportPreview` 的自动填充条件是 `cur === 0 \|\| cur < suggested`，**无法把 101 拉回 1**——新目录首次导出时界面提示「建议从 1 开始」但输入框仍是 101 | 前端初值改空（让后端/建议值决定），或把自动填充条件改为无条件采用建议值 |
| `core/scanner.py:200` 注释 | 仍写「长边 >=2160」，实际 `DEFAULT_LONG_TARGET = 1920` | 修注释，或更好：注释直接引用常量而非写死数字 |
| CHANGES「未处理」清单滞后 | 其中「`.export-view` 是否提升为真全屏（当前 880px）」一条已由同日改动完成（现为 1920px） | 收尾时回扫并划掉已完成项 |
| 试导出目录无 GC | 多次试导出堆积 `_trial_*` | 保留最近 N 版 |
| 预检结果无缓存 | 切换步骤即重算 | sortBy/scope 未变时复用 |
| 顺序列表无虚拟滚动 | 25k 张 = 2.5 万 DOM 节点 | 需与 SortableJS 权衡（见 §3.4） |
| `.og-card` 未渲染 tags 徽章 / `prevTarget` 历史批次提示 | 信息未利用 | 低优先级增强 |

## 九、给下一次改动的速查清单

**动手前**
1. 这次改动会同时碰到哪几端？（后端/预检/导出/前端）列全再动。
2. 有没有现成常量可复用？别写字面量。
3. 会不会产生静默退化分支？有的话加日志。

**动手时**
4. 新增字段：数据结构 → 白名单 → 序列化 → 前端 → 测试，五处同步。
5. 新增函数：确认模板/调用点真的绑上了。
6. 性能问题：先判断杠杆在"传了多少"还是"算了多少"；并行优先于换库。
7. 刷新逻辑：按"改了什么"选最小粒度端点。

**动手后**
8. `py_compile` / `node --check` → 单测 → curl → 实机，四层都过。
9. 对照组要做双方向断言（"没写"和"对照组会写"都要证明）。
10. 写 CHANGES，明确「承接哪份设计」+ 未处理项清单。
